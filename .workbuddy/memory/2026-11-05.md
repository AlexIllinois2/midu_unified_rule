## 决策：删厂商规则 vs 补规则（2026-11-06 分析）
CC-CEDICT 精确统计（末字为「子」的 2-4 字词条，排除 variant 条目）：
- 轻声子(zi5) 971 条；其中「子前音节为三声」= 真正被三三变调误伤的仅 182 条（121 个不同前字）
- 全声子(zi3) 304 条
结论：删掉 `子 *5 WORD_INSIDE(-1) !WORD_INSIDE(0)` 会让 971 条轻声词全部回落成 zǐ，且 182 条受害集不会自动好转（它们是轻声词，删规则后读 zǐ 仍错）——纯亏。保留规则只需覆盖 182+304=486 条。
注意陷阱：多字词看的是「紧挨子的那个字」是否三声，不是首字（打拍子 da3 pai1 zi5 本来就没问题）。
现覆盖：B 集 126/182、C 集 209/304。新补 53 条（本子/法子/篓子/卷子/杆子/摆子/小伙子/两口子/打底子/日本鬼子 等，含三三变调后表层调），位于 褶子 行下方；output 1841 行。
排除原则：多音字(卡子/角子/堡子/掸子/色子/笼子/马子/蹶子)、生僻(抿子/拶子/膙子/蟢子/虮子/趼子/馃子/饵子/袄子/纽子/埂子/侉子/崴子/广子)、含「一」的(一揽子/一股子)、地名(南海子/甘井子)、术语(密码子/吸引子)。

## 方案B（删厂商规则+合并字符表）成本核算 —— 结论：不划算
- A（现方案）：留 `子 *5 WORD_INSIDE(-1)`，写 182 轻伤 + 304 全声子 = 486 条词级规则。
- B（删厂商规则）：需 1 条「子」字符表规则（表内 589 个字）+ 55 条例外（前字与轻声词冲突的 zǐ 词）+ 182 条（三三受害救不了）= 238 条。
- 条数 B 省一半，但**性能上无差别**：引擎只有一张规则表（unified_rule.txt 1839 行 / 59KB / 1319 个触发字 / 平均 1.39 条每字），按触发字索引，规则条数不是瓶颈。不存在"厂商规则跑一遍+补丁再跑一遍"的两遍。
- 真正代价在**失效模式**：B 是"白名单"，未登录的前字一律把 子 读成 zǐ（"桌紫"级刺耳）；A 是"默认对"，只在三声前字时轻微跑调。且 B 的 55 条例外规则依赖表内容，表一改别的词会静默坏掉；A 的规则彼此独立。
- 若要压缩，更值的是把 182 条词级规则换成 121 条「前字规则」（`椅 *3 TEXT((椅)子)`），少 61 条且能覆盖词典外新词——但多音前字（长/行/角等）要排除。
- 工具：tmp/ab_cost.mjs（A/B 条数核算）、tmp/cover_check.mjs。

## 网页端「应用/推送」导致的 rule_patch.txt 内容丢失：定位与加固
- 排查结论：**不是 fd/缓存问题**。planStore.ts 每次调用 readFileSync，不持有句柄、无缓存，每次读到的都是当时磁盘内容。
- 真实丢内容四条路径：
  1. 手改的是 `unified_rule.txt`（产物）而非 `rule_patch.txt`（源）→ 每次 apply 从 vendor+patch 重生成，手改必被覆盖，100% 复现；
  2. 编辑器缓冲区与服务器写入「谁最后写」——编辑器未保存/延迟自动保存时点应用，或 apply 读到保存前内容再写回；
  3. 并发 apply：「应用」「推送」是两颗按钮、各禁各的，推送内部还会再调 applyPending，连点/多标签页会交错「读—改—写」；
  4. writeFileSync 非原子，看门狗 process.exit 或中断会留半截文件。
- 已加固（src/planStore.ts + midu_rule_updater.ts + src/web/js/app.js）：
  - 写前逐字复核（读完→算完→再读一遍比对，不一致则基于最新内容重算，最多 3 次）
  - 原子写（写 `.tmp-<pid>-<ts>` 再 rename）
  - /api/apply 全链路串行化（applyChain），杜绝并发覆盖
  - 覆盖前自动备份到 conf/.rule_patch.bak
  - 页面 hint 显示补丁真实行数/字节/mtime，以及「期间文件被外部改动，已重算 N 次」警告
- 实测：5 个并发 apply 请求 5 条规则全部落盘（planLines 585→589 递增），改造前会丢。
